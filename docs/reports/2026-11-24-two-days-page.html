섞이는 code와 짧은 계획: 11월 23일과 24일의 실험

2026-11-24 14시 KST, Claude Code가 썼다. 23일 오후부터 24일 오후까지 한 실험을 처음 읽는 사람도 따라올 수 있게 정리한다. 숫자는 모두 직접 돌려 잰 것이고, 출처가 되는 run과 스크립트는 마지막 절에 모았다. 아직 학습이 끝나지 않은 run은 그렇다고 밝혔다.

1. 들어가며

NEO는 격자 퍼즐의 입력과 출력을 보고, 그 변환을 일으킨 숨은 program을 짧은 code의 열로 적는 모델이다. 부품은 넷이다. state encoder가 격자를 칸마다의 벡터로 바꾸고, programmer가 지금 격자와 목표 격자를 보고 codebook에서 code 하나를 고르고, executor가 그 code를 격자에 적용하고, state decoder가 결과를 다시 격자로 읽는다. 과제는 support pair 둘과 query 입력 하나로 주어진다. 모델은 support를 보고 program을 적고, 그 program을 query에 실행한다. 이렇게 낸 query 답이 숨은 정답과 칸 하나 틀리지 않고 같은 비율을 transfer라고 부르고, 이 글의 숫자는 대부분 이것이다.

23일 아침까지의 관찰은 두 개의 벽으로 요약된다.

첫째 벽은 환경이 커질 때 생겼다. primitive가 8개인 환경에서는 회전과 뒤집기 계열이 90% 넘게 풀리는데, 24개로 늘리면 이 계열 일곱 개만 15% 근처로 떨어지고 나머지 17개는 80%대를 지킨다. 들여다보니 90도 회전, 270도 회전, 전치, 반대 전치가 모두 같은 code 하나로 가고 있었다. 넷은 object의 가로와 세로를 맞바꾼다는 공통점이 있다. 아래에서는 이 넷을 줄여서 가로세로를 바꾸는 넷이라고 부른다. primitive마다 정답 code를 정해 주면 같은 부품이 이 계열을 83%에서 98%로 해내므로, 부품이 모자란 것이 아니다. 정답 없이 code를 배정하는 과정에서 비슷한 변환이 한 code로 묶인 채 굳는 것이 문제였다. 이것을 라벨 없이 풀려는 열세 가지 시도는 모두 실패했다.

둘째 벽은 program이 길어질 때 생겼다. primitive 하나짜리 pair로 한 단계만 학습한 모델은 시험 때 code를 이어 쓰면 짧은 과제를 잘 풀지만, 숨은 program의 길이가 5이면 transfer가 24%, 8이면 7%로 떨어진다. 여러 단계를 한꺼번에 학습시키면 오히려 code가 primitive가 아닌 것으로 굳었으니, 한 단계 학습이 지금으로서는 나은 출발점이다. 남은 질문은 이 모델이 왜 긴 program을 이어 가지 못하느냐다.

이틀 동안 이 두 벽을 따라갔다. 긴 program 쪽은 원인을 executor와 programmer로 가르는 것부터 시작했고, 섞인 code 쪽은 학습 신호에 무엇이 빠져 있는지를 찾는 데 집중했다. 결론부터 말하면 긴 program의 병목은 programmer의 계획이었고, 섞인 code를 푸는 데 빠져 있던 것은 같은 code가 다른 입력에서도 같은 일을 하라는 요구였다.

2. 실험의 바탕

모델은 랩 NEO의 부품을 그대로 쓴다. 기준이 되는 설정은 programmer가 6층 폭 256의 transformer, executor가 4층 폭 128의 AdaLN-Zero transformer, codebook은 primitive 수의 두 배인 code를 둔다. 학습은 batch 128로 24,000스텝이다. 데이터는 BabyTheorist의 생성기를 써서 만들었고, 8개, 24개, 32개, 52개, 64개 primitive 묶음이 있다. 앞의 묶음은 뒤의 묶음에 그대로 들어간다.

판정에 쓴 숫자는 넷이다. 하나는 위에서 말한 transfer다. 둘째는 숨은 program의 길이별 transfer이고, 길이는 평가할 때 결과를 나누는 데만 쓴다. 셋째는 가로세로를 바꾸는 넷의 transfer 평균이고, 섞인 code 문제의 판정 기준으로 seed 평균 60%를 미리 정해 두었다. 넷째는 code NMI다. primitive와 programmer가 고른 code 사이의 정규화 상호정보량으로, primitive마다 자기 code를 하나씩 쓰면 1이고 섞이거나 흩어지면 낮다. 회전 계열 일곱만으로 잰 NMI는 8개 환경 0.86, 24개 환경 0.14로 transfer와 같은 순서로 갈려서 진단에 썼다.

seed는 대개 셋에서 다섯을 돌리고 평균으로 판단했다. seed마다 결과가 크게 갈리는 경우가 많아서, 한 seed의 숫자는 그렇다고 밝혔다.

3. 긴 program이 실패하는 이유

3.1 탐색을 넓히면 얼마나 오르는가

첫 시도는 모델을 다시 학습하지 않고 program을 찾는 방식만 바꾸는 것이었다. 지금까지는 매 단계 programmer가 가장 가깝다고 한 code 하나만 실행했다. 이것을 greedy라고 부른다. 대신 단계마다 programmer가 가깝다고 한 code를 여러 개 실행해 보고, 그 가운데 상위 몇 갈래만 다음 단계로 넘긴다. 넘기는 갈래의 수를 폭이라고 부른다. 실행 결과가 support 출력과 똑같아지면 그 code 열을 후보로 기록하고, 둘째 support pair에도 맞는지 확인한 다음 query에 쓴다.

갈래를 줄 세우는 기준에서 한 번 실수했다. 처음에는 지금 격자가 support 출력과 얼마나 가까운지로 줄을 세웠는데, 폭 4가 폭 1보다 나빴다. 여러 단계 program의 중간 격자는 맞는 길 위에 있어도 목표와 멀 수 있어서, 맞는 길이 일찍 잘린 것이다. 그래서 programmer가 각 code를 얼마나 선호했는지를 단계마다 누적한 점수로 줄을 세우도록 바꿨다. 이렇게 하면 폭 1은 정확히 greedy와 같다.

8개 환경에서 한 단계로 학습한 모델 seed 여섯을 레벨 1, 5, 7의 평가 과제로 잰 결과가 아래다.

숨은 길이 폭 1 폭 4 폭 16
1 85% 85% 86%
3 44% 56% 66%
5 24% 32% 44%
8 7% 12% 22%

다시 학습하지 않았는데도 길이 5에서 8 사이가 두세 배가 된다. 하지만 길이 8에서 22%는 여전히 낮다. 폭 16으로도 과제의 70%쯤은 두 support를 모두 재현하는 program을 아예 찾지 못했다. 거꾸로, 두 support를 통과한 program이 query에서 틀리는 비율은 긴 program에서 20%에서 30%였다. 손실의 더 큰 부분은 거짓 통과가 아니라 찾지 못하는 데 있었다.

3.2 executor인가 programmer인가

찾지 못하는 이유는 둘 중 하나다. executor가 여러 단계를 이어 실행하는 동안 오차가 쌓여 결과가 틀어지거나, programmer가 맞는 code를 후보에 올리지 못하는 것이다. 이를 가르려고 라벨을 쓰는 진단을 했다. primitive마다 길이 1 과제에서 가장 자주 정확히 재현한 code를 그 primitive의 code로 정하고, 숨은 program을 그 code의 열로 바꿔 query에 그대로 실행했다. programmer를 건너뛰고 executor만 시험하는 셈이다.

seed 정답 program 그대로 실행 탐색 폭 16 greedy
42 92% 30% 11%
45 97% 42% 12%
47 66% 34% 13%
44 49% 18% 4%
43 39% 5% 0%
46 1% 0% 0%

길이 8의 query 정답률이다. code가 깨끗한 seed 42와 45에서 executor는 여덟 단계를 이어 실행해도 92%와 97%를 맞혔다. 그러니 긴 program에서 떨어지는 원인은 executor가 아니라 programmer다. 이 programmer는 학습할 때 언제나 한 단계 떨어진 목표만 봤다. 목표가 여러 단계 떨어져 있을 때 지금 무엇부터 해야 하는지는 배운 적이 없다. 반면 seed 43, 44, 46은 상한부터 낮았는데, 가장 자주 쓰인 code 하나가 그 primitive를 온전히 맡지 못할 만큼 code가 갈라져 있었기 때문이다. 이 seed들의 문제는 4절에서 다룰 code 배정 쪽에 있다.

3.3 꿈으로 먼 목표를 가르친다

programmer에게 먼 목표를 가르치려면 여러 단계 떨어진 목표와 그때의 올바른 첫 code가 필요하다. 숨은 program을 쓰면 쉽지만 그것은 라벨이다. 대신 모델이 스스로 만든다. 학습 데이터의 입력 격자에서 출발해, programmer가 실제 학습 pair에서 고르는 code들 가운데 1개에서 8개를 고르는 빈도에 비례해 뽑는다. 얼린 executor로 그 열을 실행하면서 단계마다 격자로 읽어 다음 단계에 넘긴다. 마지막 격자를 목표로 삼고, 중간 격자마다 다음에 실행한 code를 programmer가 맞히게 학습한다. 격자를 바꾸지 않은 단계와 이미 지나온 격자로 돌아가는 단계는 그 code가 목표로 가는 길이 아니므로 뺀다. programmer만 배우고 나머지 부품은 얼린다. 깨어 있는 동안 확정된 executor로 잠에서 꿈을 꾸어 programmer만 고치는 것과 같아서, 아래에서는 이것을 꿈 학습이라고 부른다.

꿈 학습을 6,000스텝 하자 폭 16에서 길이 8의 transfer가 여섯 seed 평균 22%에서 38%로 올랐다. 대가도 있었다. greedy로 쓰면 길이 1이 85%에서 76%로 떨어졌다. 먼 목표를 주로 배우면서 한 단계짜리 결정이 흐려진 것이다.

3.4 검증된 실제 pair를 섞는다

그 손실을 막으려고 꿈 위치의 절반을 실제 학습 pair로 채웠다. 실제 pair마다 모든 code를 실행해 보고, 어떤 code 하나가 그 pair를 정확히 재현할 때만 그 code를 목표로 삼아 남긴다. 한 단계짜리 pair를 숨은 깊이 대신 executor의 실행으로 골라내는 것이다.

숨은 길이 폭 16: 전 / 꿈만 / 섞음 greedy: 전 / 꿈만 / 섞음
1 86% / 86% / 87% 85% / 76% / 86%
3 66% / 68% / 70% 44% / 43% / 62%
5 44% / 56% / 58% 24% / 27% / 41%
8 22% / 38% / 42% 7% / 21% / 24%

길이 1의 손실이 사라졌고, 긴 program은 꿈만 했을 때보다 더 올랐다. greedy가 특히 좋아져 길이 3이 44%에서 62%가 됐다. 폭 16 길이 8을 seed별로 보면 seed 45가 42%에서 74%, seed 42가 30%에서 65%다. 꿈은 먼 목표로 가는 첫걸음을, 검증된 실제 pair는 한 단계짜리 결정을 가르친다고 볼 수 있다. 꿈 학습을 네 배로 늘려 24,000스텝 해 보니 seed 42에서 2에서 4%p 더 오르고 seed 45는 그대로였다. 양을 늘리는 쪽은 수확이 줄어든다.

3.5 남은 거리를 어림해 탐색을 이끈다

꿈에서는 각 중간 격자에서 목표까지 격자를 바꾸는 단계가 몇 개 남았는지를 정확히 안다. 이것을 맞히는 작은 network를 꿈으로 학습시켰다. programmer와 같은 꼴에 4층 폭 128이고, 0에서 8까지의 분포를 낸다. 탐색은 지금까지의 누적 비용에 이 예측의 기댓값을 더해 갈래를 줄 세운다. A* 탐색이 남은 거리를 어림하는 것과 같은 역할이다. 아래에서는 이것을 남은 거리 예측기라고 부른다. 그림에서는 critic h로 적었다.

꿈 학습과 실제 pair를 섞은 모델 seed 42와 45에 붙여 본 결과, 효과는 폭이 좁을 때 컸다. seed 45 레벨 7에서 폭 4의 transfer가 67.5%에서 74.3%로, 레벨 5에서 80.4%에서 85.4%로 올랐다. 폭 16에서는 76.2%에서 78.9%, 86.8%에서 88.8%로 오름폭이 작다. seed 42도 폭 4에서 3에서 5%p, 폭 16에서 1%p쯤 올랐다. 넓게 찾을 여유가 없을 때 어디를 찾을지 알려 주는 쪽으로 쓸모가 있다.

3.6 24개 환경의 깨끗한 code 위에서

여기까지는 8개 환경이었다. 4절의 방법으로 24개 환경에서 code를 깨끗하게 세운 모델에 같은 꿈 학습을 얹었다. 24개 primitive로 길이 5 이상의 평가 과제를 만드는 일은 생성기가 더 짧은 program이 없는지 확인하는 탐색이 너무 오래 걸려 포기했고, 기존 평가 파일의 길이 4까지로 쟀다.

한 pair 랩 설정, seed 42 60%, 39%, 22%, 6% 60%, 39%, 20%, 11%
두 pair hard EM, seed 42 99%, 93%, 72%, 47% 100%, 96%, 76%, 53%
두 pair hard EM, seed 45 98%, 87%, 64%, 37% 98%, 91%, 73%, 52%
두 pair hard EM, seed 46 98%, 90%, 69%, 45% 98%, 93%, 74%, 58%

code가 깨끗한 모델에서 꿈 학습은 길이 4를 세 seed 평균 43%에서 54%로 올렸다. 평가 파일 전체로는 seed 42가 94%로, 같은 평가에서 랩 설정의 43%의 두 배를 넘는다. code가 섞인 한 pair 랩 모델에서는 거의 효과가 없었다. 계획을 가르치기 전에 code가 깨끗해야 한다.

4. 섞인 code가 갈라지지 않는 이유

4.1 pair 하나만 보면 쪼개든 섞든 상관이 없다

code를 숨은 변수로 보고 EM으로 배정하는 것은 이미 23일 새벽에 해 봤다. 그때는 넷이 이미 한 code로 굳은 run의 끝에서 시작했으니, 모든 code가 섞인 pair에 비슷하게 틀린 상태였다. 이번에는 처음부터 학습했다. soft EM은 pair마다 모든 code를 실행해 재현 오차로 책임 비율을 정하고 온도를 서서히 내린다. hard EM은 pair마다 가장 잘 재현하는 code 하나에만 그 pair를 주고, executor를 그 code로 학습하며 programmer가 그 선택을 따라 하게 한다. hard EM에는 아무도 고르지 않는 code에 작은 보너스를 조금씩 쌓아 주어 되살리는 장치를 붙였다.

조건, seed 셋 가로세로를 바꾸는 넷 나머지 17개
랩 설정 17% 84%
soft EM 25% 95%
hard EM 21% 66%

둘 다 기준 60%에 한참 못 미쳤다. hard EM이 나머지 17개까지 깎은 모양이 원인을 보여 준다. 그 17개는 support를 98%에서 100% 재현하는데 transfer는 69%였고, primitive 하나에 code가 평균 2.8개 붙어 있었다. pair마다 그 pair만 가장 잘 맞히는 code를 주면, code가 변환이 아니라 특정 모양의 입력을 다루는 전문가로 쪼개진다. 넷이 한 code로 섞이는 것과 한 primitive가 여러 code로 쪼개지는 것은 같은 뿌리에서 나온다. 학습 과제가 pair 하나뿐이면 어떤 code든 그 pair만 재현하면 loss가 0이어서, 섞이든 쪼개지든 학습은 그것을 구별하지 못한다. 평가는 다르다. support에서 고른 code가 다른 object의 query에도 맞아야 한다.

4.2 pair 둘을 한 과제로 주면

빠져 있는 것은 같은 code가 다른 입력에서도 같은 일을 하라는 요구다. 이것을 넣으려고 학습 과제를 같은 program을 서로 다른 object 둘에 적용한 pair 둘로 줬다. 숨은 program의 이름은 쓰지 않지만, 어느 pair끼리 같은 규칙인지는 알려 준다. ARC의 과제가 이런 형식이고, 랩의 GridWorld 코드도 본래 이렇게 학습한다. 랩 모델은 첫 pair에서 고른 code를 두 입력에 모두 실행해 학습하고, hard EM은 두 pair의 오차 합이 가장 작은 code를 고른다. 데이터는 24개 묶음의 단일 primitive 과제 4만 개, pair 8만 개로, pair 하나로 학습할 때 쓰던 7만 5천 개와 양을 맞췄다.

조건 가로세로를 바꾸는 넷, seed별 평균 나머지 17개
랩 모델, pair 하나 16, 15, 20 17% 84%
랩 모델, pair 둘 35, 34, 34 34% 88%
hard EM, pair 둘 96, 35, 37, 83, 71 셋 56%, 다섯 64% 97%

pair의 묶음만으로 랩 모델의 넷이 두 배가 됐다. hard EM은 seed 42에서 회전 계열 일곱이 97%, 나머지가 99%로, 정답 code를 준 진단과 같은 수준까지 라벨 없이 갔다. 처음 정한 seed 셋으로 보면 평균 56%라 기준에 못 미치고, seed 사이의 차이가 효과만큼 커서 둘을 더 돌린 다섯으로 보면 64%로 넘는다. 둘 다 그대로 적는다. 나머지 17개도 97%로 올라 입력별 전문가 code가 사라졌다. code가 깨끗해지자 여러 단계 과제도 따라 나아져서, 24개 환경에서 greedy의 길이 2가 35%에서 78%가 됐다.

처음에는 둘째 pair가 혼동을 깨 준 덕이라고 생각했다. 90도와 270도 회전은 180도 대칭인 object에서 같은 결과를 내므로, pair 하나로는 둘을 구별할 수 없는 경우가 있다. 라벨을 쓰는 진단으로 세어 보니 이런 혼동은 회전 계열 과제의 7%에서 18%뿐이었다. 게다가 첫 pair만 볼 때와 두 pair를 다 볼 때의 수가 똑같았다. 생성기가 pair가 둘 이상인 과제를 만들 때, 첫 pair를 재현하는 짧은 program이 모두 마지막 pair도 맞히는 경우만 남기기 때문이다. 평가 과제에서 support 하나로 답이 정해지게 하려는 조건인데, 학습용 과제에도 같은 함수가 쓰였다. 그러니 두 pair 학습이 통한 이유는 혼동을 깨서가 아니라, 다른 object에서도 같은 일을 하라는 요구로 입력별 전문가 code를 막아서다.

4.3 멈춘 seed는 다시 열리지 않았다

hard EM의 다섯 seed 가운데 43과 44는 넷을 code 하나에 둔 채 35% 근처에서 멈췄다. 기록을 보면 멈춘 seed에는 쓰이지 않는 code가 남아 있었는데도, 그 code를 되살리는 보너스가 거의 쌓이지 않았다. 갈라진 seed 42에서는 3,000스텝에 상한까지 쌓였다. 갈라짐은 2,400스텝과 7,200스텝 사이에 정해졌다. 이 고착을 푸는 다섯 가지 방법을 시험했고, 하나도 평가를 움직이지 못했다.

보너스를 열 배로 키우자 seed 43, 44, 45가 37%, 96%, 35%가 되어 어느 seed가 풀리느냐만 바뀌었다. 온도를 10에서 0.01로 처음 6,000스텝에 걸쳐 내리는 형태는 다섯 seed가 50%, 73%, 51%, 61%, 50%로, 멈추는 seed는 없어졌지만 완전히 풀리는 seed도 없어 평균 57%였다. 넷이 한 덩어리로 묶이던 것이 둘이나 셋짜리 작은 덩어리로 바뀐 것이다. 그 끝에서 온도를 다시 올렸다 내려도 덩어리는 그대로였다.

잠에서 섞인 code를 직접 나누는 방법도 해 봤다. 섞인 code의 과제를 programmer 출력으로 k-means해 나누려 했지만, 숨은 primitive로 잰 묶음의 순도가 0.28로 우연 수준 0.25와 같았다. programmer 출력에는 넷을 가를 정보가 남아 있지 않다. 그래서 executor가 나누게 했다. 섞인 code가 가장 못 맞히는 과제 하나를 본보기로 쓰이지 않던 code를 학습시키고, 섞인 code의 과제를 두 pair를 더 잘 재현하는 쪽으로 다시 나누기를 되풀이했다. 학습 과제의 두 pair 재현은 35%에서 94%로 올랐지만 평가는 34%로 그대로였고, 폭 16으로 넓게 찾아도 마찬가지였다. 새 code들이 변환을 배운 것이 아니라 그 과제의 object를 외운 것으로 보인다. 그 상태에서 깨어 12,000스텝 더 학습해도 33%로, 나누지 않은 대조의 35%와 같았다.

4.4 잘 풀린 seed를 라벨 없이 알아보기

고착을 풀지 못한다면, 잘 풀린 seed를 알아보고 고르는 길이 있다. 학습에 쓰지 않은 두 pair 과제 4,000개를 깊이를 섞어 새로 만들고, programmer가 첫 pair를 보고 고른 code가 두 pair를 모두 재현하는 비율을 점수로 삼았다. 숨은 program도 깊이도 읽지 않는다. 두 형태의 hard EM 열 run에서 이 점수와 가로세로를 바꾸는 넷의 순위 상관이 0.98이었고, 점수가 가장 높은 run이 넷 96%인 seed 42였다. 섞인 code는 두 pair를 함께 재현하지 못하니 점수가 낮아지는 것이다. seed 몇 개를 돌려 이 점수로 고르면 라벨 없이 잘 풀린 run을 얻는다. 같은 점수를 학습 도중에 보면, 잘못 굳은 run을 일찍 알아보고 다시 시작하는 데도 쓸 수 있다.

4.5 깊이를 읽지 않고 한 단계 과제 고르기

지금까지의 두 pair 과제는 숨은 깊이가 1인 것만 골라 만들었다. 벤치마크 규칙에서는 깊이를 학습에 쓸 수 없다. 그래서 레벨 1처럼 깊이를 섞은 두 pair 과제 13만 3천 개를 만들고, hard EM이 batch마다 가장 잘 맞는 code의 오차로 과제를 줄 세워 절반만 학습하게 했다. 여러 단계 과제는 code 하나로 설명되지 않아 오차가 크니 깊이를 읽지 않고도 빠진다. 끝난 seed 43은 넷 33%, 나머지 99%이고, seed 42와 44는 16,800스텝에서 32%와 33%다. 깊이로 고른 데이터에서 96%까지 갔던 seed 42가 여기서는 아직 갈라지지 않았다. 나머지 primitive는 잘 배우지만, 섞인 code를 가르는 데는 깊이로 고른 데이터보다 불리한 것으로 보인다. 아직 끝나지 않은 run이라 끝값을 보고 판단한다.

5. 지금의 최선

이틀의 결과를 합치면 지금의 최선은 네 단계다. 같은 program의 pair 둘로 된 과제에서 hard EM으로 한 단계 code를 세운다. seed 몇 개를 돌려 라벨 없는 검증 점수로 하나를 고른다. 그 위에 꿈 학습과 검증된 실제 pair로 programmer의 계획을 보강한다. 평가 때는 support로 검증하는 탐색을 쓰고, 폭이 좁을 때는 남은 거리 예측기를 더한다.

6. 한계와 다음 일

가장 큰 한계는 pair의 묶음을 쓴다는 점이다. 숨은 program보다 약한 신호이지만 아무것도 없는 것보다는 강하다. 벤치마크의 학습 파일은 pair 하나짜리이므로, 이 방법을 벤치마크 규칙 안에서 쓰려면 같은 code로 서로를 재현하는 pair를 모아 묶음을 스스로 찾아야 한다. 랩이 과제 묶음을 학습에 허용하는지에 따라 이 일의 무게가 달라진다.

둘째로, 처음에 굳은 배정을 푸는 방법은 아직 없다. 지금은 여러 seed 가운데 고르는 것으로 피해 가고 있다. 섞인 code를 나누려는 시도는 모두 새 code가 외우는 쪽으로 갔다. 나눈 code가 처음부터 많은 과제를 받도록 하는 방법이 필요해 보인다.

셋째로, 긴 program은 상한에 한참 못 미친다. 8개 환경 길이 8에서 최고 74%이고 상한은 97%다. 꿈의 양을 늘리는 쪽은 수확이 줄었으니, 꿈의 길이 분포나 남은 거리 예측기를 programmer 학습에 직접 쓰는 쪽을 볼 생각이다.

넷째로, 24개 이상의 환경에서는 길이 5 이상의 평가 과제가 없다. 생성기의 최단 program 확인을 싸게 만들어야 긴 program을 큰 환경에서 잴 수 있다.
