# 2026-11-20 논의 기록: 연구를 두 축으로 다시 짜기

2026-11-20 KST 오후. 사용자와 Claude Code가 나눈 논의를 순서대로 적는다. 사용자의 말은 따옴표 안에 그대로 옮겼다. 이 기록은 고치지 않는다. 뒤에 생각이 바뀌면 새 기록을 더한다.

## 1. 사용자의 제안

같은 날 오전까지 이전 레포 `neo-vocabulary-restructuring`에서 작은 세계의 실험을 하고 있었다. 그 결과 보고를 받은 뒤 사용자가 말했다.

"우리 neo 연구 있잖아. 주제를 아무래도 두 축으로 가져가면서 완전히 재구성해야할 것 같아. 첫째는 scaling이야. multi object neo라던지, program length라던지, primitive 개수라던지, 둘째는 Evaluation이야. 지금 neo는 transferability만 있는데, 내 생각에는 Agent가 필요할 거 같아. NEO의 theory가 좋은지 판단할 방법이 없어. 어떻게 생각해? 결국 지금 NEO에 달 수 있는게 두 개인거 같은데, 너무 날개를 달 생각을 하지 말고, 분석을 통해서 나올 수 있는 아주 당연한 질문을 던지는게 맞다고 생각해. NEO는 지금 부족함 투성이거든."

## 2. Claude Code의 첫 답

방향에 동의했다. 이유로 든 것은 이전 레포의 경험이다. NEO가 어디서 왜 틀리는지 모르는 채로 새 부품을 얹으면, 결과가 나쁠 때 본체가 틀린 것인지 얹은 부품이 틀린 것인지 가를 수 없다. 이전 레포에서 열흘 동안 남아 있던 실패의 원인이 NEO가 아니라 그 위에 얹은 채점 조건에 있었다.

두 가지를 다르게 보았다.

첫째, scaling과 evaluation을 나란히 두지 말고 evaluation을 먼저 하자고 했다. scaling 실험에서 program이 길어질 때 정확도가 떨어져도, 최종 정확도 하나로는 틀린 것이 executor인지 programmer인지 codebook인지 알 수 없기 때문이다.

둘째, Agent는 evaluation의 첫 단계가 아니라 마지막 단계라고 했다. Agent가 목표에 닿지 못했을 때 executor의 예측이 틀린 것인지, 예측은 맞는데 code의 열을 찾는 탐색이 못 찾은 것인지가 섞이기 때문이다. 정답 program이 있는 데이터에서는 더 직접 잴 수 있는 것이 있다고 하고 다음을 들었다.

1. 정답 primitive 하나가 일으킨 변화를 가장 많이 맞히는 code 하나를 찾아, 그 code가 그 변화 가운데 몇 %를 맞히는지 잰다. primitive가 code 여럿에 쪼개졌는지가 나온다.
2. 그 code를 학습 때 쓰인 적 없는 state에서 실행해도 같은 일을 하는지 본다.
3. 정답 program에 해당하는 code들을 학습 때보다 길게 이어 실행하고 길이에 따른 정확도를 잰다.
4. 시작 state와 목표 state를 주고, 배운 executor로 code의 열을 미리 실행해 보며 목표에 닿는 열을 찾은 뒤, 진짜 환경에서 실행해 닿는 비율을 잰다. 이것이 Agent에 해당한다. 탐색은 짧은 열부터 모두 실행해 보는 고정된 방법으로 둔다.

scaling의 세 방향에 대해서는 종류가 다르다고 했다. program length와 primitive 개수는 같은 NEO에서 숫자를 키우는 것이다. multi object는 code를 어느 object에 적용할지 정하는 부품이 필요해서 새 부품을 만드는 일이다.

program이 길어질 때 막히는 이유의 후보도 셋 들었다. executor가 낸 state에 다음 code를 실행하면 어긋난다. programmer가 긴 code의 열을 고르지 못한다. primitive 하나가 code 여럿으로 쪼개져 있다. 뒤에 코드를 읽고 첫째 후보를 고쳤다. 랩 NEO의 정식 추론은 이미 스텝마다 격자로 풀었다가 다시 읽으므로, 이 후보는 추론이 아니라 학습 쪽의 문제다.

이전 레포에서 가져올 것은 부품이 아니라 측정 둘이라고 했다. 아는 primitive가 n개일 때 다음 하나를 익히는 데 든 sample 수, 그리고 과제 하나를 푸는 데 executor를 실행한 횟수다.

## 3. evaluation을 메인으로

사용자가 받았다.

"오케이. 그래서 네 생각은 Evaluation 먼저 끝내자는거지? 그럼 evaluation 을 메인 주제로 잡고, scaling을 sub task로 생각해보자. evaluation 어떻게 연구 진행해볼까?"

Claude Code는 랩 NEO 코드를 읽은 뒤 계획을 냈다. 질문은 하나로 잡았다. transfer 정확도가 같은 두 NEO가 있을 때 어느 쪽 theory가 더 좋은지 가를 수 있는가, 그리고 그 판정이 아직 풀어 보지 않은 과제에서의 정확도를 맞히는가. 순서는 넷이었다. 이 레포에 있던 GridWorld에서 평가할 모델들을 학습한다. 측정을 평가 부품으로 만든다. 측정 도구가 쓸모 있는지 시험한다. 그 뒤에 scaling을 한다.

측정 도구의 시험으로는 셋을 들었다. programmer가 맞는 code의 열을 고르는 비율에 executor가 그 열을 맞게 실행하는 비율을 곱해서 transfer 정확도를 다시 계산해 보고 실제 값과 견준다. 짧은 program에서 잰 측정값으로 긴 program에서의 정확도를 맞혀 본다. codebook을 일부러 너무 작게 또는 너무 크게 줘서 결함을 심고 측정이 그것을 잡는지 본다.

## 4. 사용자의 반대와 그 뒤의 합의

사용자가 순서를 뒤집었다.

"음.. 내생각에는 그냥 primitive 더 많고 program length 더 길고 multi object인 상황을 만들어서 거기에 맞는 NEO도 만들고, 학습도 시켜서 무슨 문제가 생기는지 관찰부터하는게 먼저 아닐까?"

Claude Code는 사용자가 맞다고 답했다. 측정 도구를 시험하는 일을 실패를 보기도 전에 놓은 것이 틀린 순서였다. 어떤 측정이 필요한지는 NEO가 어떻게 틀리는지를 봐야 정해진다. 그리고 이동 넷에 object 하나인 GridWorld에서는 NEO가 대체로 풀 가능성이 높아서 측정을 만들어도 가를 것이 없을 수 있다. 뒤의 것은 추측이다.

다만 세 가지를 고쳐서 하자고 했다.

1. 상황을 새로 만들지 말고 BabyTheorist를 쓴다. object의 수, program의 길이, primitive의 수가 모드와 레벨로 이미 나뉘어 있다.
2. 거기에 맞는 NEO를 먼저 만들지 말고 지금 NEO를 그대로 돌린다. 새 NEO를 먼저 만들면 틀렸을 때 새 부분이 틀린 것인지 NEO가 원래 못 하는 것인지 가를 수 없다. 지금 NEO가 어떻게 틀리는지가 무엇을 만들어야 하는지를 정한다.
3. 세 방향을 한 설정에 한꺼번에 키우지 말고, 방향마다 따로 키운 설정을 나란히 돌린다.

관찰할 때 볼 것도 둘 정했다. 틀린 과제의 입력, 정답, 예측 격자를 그림으로 직접 보는 것, 그리고 NEO가 고른 code 번호와 정답 primitive를 센 표다.

evaluation이 메인 주제라는 것은 이 순서에서도 유지된다. 관찰에서 나온 실패의 종류마다 그것을 잡아내는 측정을 만드는 일이 evaluation 연구가 된다.

사용자가 답했다.

"오케이. 레포는 새로 만들자. https://github.com/minjunjee/toy-NEO.git 여기서 작업 해줘."

이어서 연구 계획을 구체화하라고 했고, 진행 방식을 정했다.

"이전처럼 chat/ code/ 번갈아가면서 진행할거야. 레포 대충 initialization해주고 Push해줘. chat에서 이어서 확인할게. 그러니까 논의된 사항들도 다 md 으로 넣어놔."

## 5. 답을 받지 못한 질문

Claude Code가 물었고 사용자가 아직 답하지 않은 것이다.

1. Agent가 뜻하는 것이 배운 theory로 목표에 닿는 것인가, 무엇을 실험할지 스스로 고르는 것인가. 앞의 것은 측정 하나이고, 뒤의 것은 action을 고르는 방법을 새로 연구하는 일이다.
2. 랩에서 NEO를 BabyTheorist에 돌릴 때 쓴 학습 코드와 체크포인트를 받을 수 있는가.
3. 사용자가 말한 transferability가 이 문서들에서 transfer 정확도라고 부르는 것과 같은가.
4. 세 가지 수정에 사용자가 모두 동의한 것인가. 사용자의 답은 "오케이"였고 항목별로 확인하지는 않았다.
